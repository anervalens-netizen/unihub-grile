# S1 architectural decisions

| # | Decision | Rationale | Alternatives considered | When to revisit |
|---|---|---|---|---|
| D1 | Stack: Python 3.12, FastAPI 0.115, SQLAlchemy 2.0, Pydantic 2.9, Alembic 1.13, PostgreSQL 17, React 18 + Vite 5 + TypeScript 5 | Pinned by AGENTS.md; matches the standalone deployment target. FastAPI keeps the read/web layer explicit so Google I/O never reaches the request thread. | Django, Litestar, Lit/HonoJS frontends. | Only on a major version bump. |
| D2 | One durable worker is started via `python -m ugrile.worker.worker`; the API layer never executes jobs | The contract is explicit: the worker is the **sole** authority that settles typed jobs. The API can enqueue or list but cannot run a job inline; the previous attempt's `POST /worker/run` and `POST /ingest/fixture/run` were removed because they violated the single-authority rule. | Celery, RQ, Dramatiqi, dedicated queue. | Stage 2 when the Google adapter arrives and the worker becomes the only async driver. |
| D3 | AC-02 enforced at three layers: pure domain (`ugrile.domain.calendar`), Postgres partial unique indexes (`uq_site_day_one_working`, `uq_person_day_one_working`), AND a real concurrent PostgreSQL integration test (`tests/integration/test_postgres_concurrent_ac02.py`) | Defence in depth. Domain gives precise error messages before persistence; DB is the absolute authority for concurrent transactions. The integration test races two threads against the partial unique indexes on a real PG server so the SQLite-only path cannot pass by accident. | Application-level row locking; SERIALIZABLE isolation level. | If concurrent assignment throughput exceeds 100/s/store we revisit. |
| D3b | Composite-tenant integrity on every foreign reference plus tenant-encoded synthetic IDs | Store and person IDs embed the tenant slug (`store_<tenant>_<code>`, `person_<tenant>_<code>`); every FK on `stores`/`people` is composite `(tenant_id, target_id) -> (tenant_id, id)`. The DB rejects a cross-tenant reference because the composite columns would not match. Upsert lookups in the connector query by `(tenant_id, internal_code)`, never by primary key, so two tenants with the same internal code never collide. | DB triggers that cross-check tenant consistency; application-only checks. | Never — composite FKs are the standard SQL way to express the invariant. |
| D4 | Connector types live in `ugrile.connectors.v1_types` and are validated by Pydantic | Pydantic gives us strict structural validation; the application never imports data shape from Retail/grile-salarii at S1. | JSON Schema, dataclasses + manual validation. | Stage 7 when Retail v1 contract lands. |
| D5 | Auth is a skeleton: `X-Ugrile-Identity` + `X-Ugrile-Tenant` headers, `services.auth` enforces role checks | S1 must prove the manager scope seam without committing to an SSO provider. Real identity is owned by the host (DSH session). | OAuth2 dependency at S1, custom JWT, third-party auth-as-a-service. | Stage 2 when manager login flow lands. |
| D6 | Health/readiness probes use dedicated endpoints, not auth | Liveness and readiness are consumed by host probes and load balancers; they must not depend on identity. | Same endpoint with optional auth. | Never. |
| D7 | Sales authority stays inside `SalesStoreDay` (immutable, generation-keyed) | The contract says the physical total is immutable and only its presence is updated; we never overwrite. | `Sales` table with mutable amount. | Stage 3 when attribution lands. |
| D8 | One Alembic migration (`0001_initial_schema`) | The schema is small and tightly coupled; one migration is easier to review than many incremental ones at this size. | Per-domain migrations. | Stage 4 when schema grows > 50 tables or needs concurrent branches. |
| D9 | Frontend built with Vite + React + TS, dev proxying `/api` to FastAPI | Same shape as the future production build; Vite is the AGENTS.md-prescribed stack. | Next.js, Remix. | Stage 4 when SSR becomes useful. |
| D10 | SQLite is the unit-test database | Fast feedback for unit tests. The partial unique index DDL is identical to PostgreSQL (verified in `tests/repositories/test_db_constraints.py`); the cross-dialect run is documented in `docs/operations/local-commands.md`. | testcontainers Postgres per test. | Stage 2 if Postgres-specific features (e.g. advisory locks) become required. |
